# Recurring events and invitations

The CLI and MCP share the same calendar adapter, local validation, and permission
checks. Calendar discovery and event listing remain read operations. Event
creation/editing/deletion operate on CalDAV resources using strong ETags.

## Recurring events

Create a series by adding an iCalendar recurrence rule:

```sh
i4d events create --calendar Work --summary 'Daily check-in' \
  --start 2026-10-30T10:00:00Z --end 2026-10-30T10:15:00Z \
  --rrule 'FREQ=DAILY;COUNT=5'
```

Use `events list` to obtain the resource path and each occurrence's original
recurrence identifier. For an existing recurring resource, select the scope
explicitly:

```sh
# Change the series, preserving existing exceptions.
i4d events edit --calendar Work --path /ACCOUNT/calendars/WORK/EVENT.ics \
  --scope series --summary 'Daily stand-up'

# Move one occurrence. The recurrence ID is its ORIGINAL start, not its new start.
i4d events edit --calendar Work --path /ACCOUNT/calendars/WORK/EVENT.ics \
  --scope occurrence --recurrence-id 2026-10-31T10:00:00Z \
  --start 2026-10-31T12:00:00Z --end 2026-10-31T12:15:00Z

# Remove one occurrence, leaving the other occurrences intact.
i4d events delete --calendar Work --path /ACCOUNT/calendars/WORK/EVENT.ics \
  --scope occurrence --recurrence-id 2026-11-01T10:00:00Z --force
```

Recurrence writes support daily, weekly, monthly, and yearly rules; sub-daily
frequencies are rejected. Occurrence membership checks are bounded to 10,000
instances; unsupported recurrence forms fail before writing.

For a new non-UTC timezone, the adapter generates a `VTIMEZONE` covering the
whole finite series. Supply `COUNT` (at most 10,000) or `UNTIL`; a new unbounded
local-time series is rejected. UTC series may be unbounded. Existing server
`VTIMEZONE` components are preserved. Definitions generated by i4d are regenerated
when extending or rescheduling the series, so the recurrence cannot silently
outgrow their daylight-saving coverage.

Use date-only recurrence IDs for all-day events and RFC3339 timestamps for timed
events. `--timezone` selects the stored timezone when supplying start/end;
account timezone defaults apply when rescheduling. Otherwise the event timezone
is preserved. `--rrule ''` clears a recurrence rule on a series
edit. Recurrence rules cannot be changed for an individual occurrence. "This and
future" editing is not exposed: choose the whole series or one occurrence.

A local preview (`--dry-run --json`) checks argument syntax without credentials or
network requests. It cannot verify that an occurrence belongs to the series, that
the resource exists, that its timezone/recurrence is compatible, or that the server
will permit a write. Remote validation happens before the conditional write.

## Invitations and attendee responses

Scheduling has its own Send capability. `readonly` and `editor` profiles cannot
send invitations, responses, or cancellations. Ordinary event edits/deletes reject
resources with organizer/attendee scheduling information; use the explicit
scheduling commands so an ordinary calendar edit cannot implicitly notify people.

```sh
# Create and send an invitation.
i4d events invite --calendar Work --summary 'Planning' \
  --start 2026-10-30T14:00:00Z --end 2026-10-30T15:00:00Z \
  --attendee alice@example.com --attendee bob@example.com

# Change an organizer-owned invitation and notify its attendees.
i4d events invite --calendar Work --path /ACCOUNT/calendars/WORK/EVENT.ics \
  --attendee alice@example.com --summary 'Planning, revised'

# Respond as an attendee.
i4d events respond --calendar Work --path /ACCOUNT/calendars/WORK/EVENT.ics \
  --partstat ACCEPTED

# Cancel an organizer-owned invitation.
i4d events cancel --calendar Work --path /ACCOUNT/calendars/WORK/EVENT.ics
```

The authenticated principal's calendar addresses determine which organizer or
attendee identity is permitted. `--organizer EMAIL` and `--attendee EMAIL` can
select an identity explicitly; they cannot impersonate another principal.
Omitted identities are discovered remotely, and ambiguous choices require an
explicit address. An Apple Account login is not assumed to be its scheduling
address. Response values are `ACCEPTED`, `DECLINED`, and `TENTATIVE`.

Every scheduling command requires terminal confirmation or explicit `--force`.
`--no-input` never authorizes a send. `--dry-run` produces a local preview and does
not discover identities or send notifications. A preview reports that those
remote checks have not occurred. Calendar scheduling uses the server's advertised
CalDAV scheduling support; unsupported servers fail explicitly. A successful
resource write is not proof that every recipient received an invitation.

Recurring invitation changes use the same `--scope` and `--recurrence-id` inputs.
Only the organizer can cancel, and attendee responses update the selected
attendee's participation state. Network errors after a scheduling write can leave
an uncertain outcome: inspect the event before retrying. There are no automatic
retries.

## MCP authorization

Scheduling tools are `events_invite`, `events_respond`, and `events_cancel`.
The MCP operator must enable `--allow-write --allow-send --force` and the selected
permission profile/exact allowlist must allow the matching command. Cancellation
also requires `--allow-delete`. Tool inputs
cannot authorize themselves or change credentials. Calendar mutation tools accept
recurrence rule/scope/recurrence identifier fields with the same validation as the
CLI. Use explicit tool allowlists to narrow the server surface.

Tests use local CalDAV fixtures and do not send real invitations. Live scheduling
and recurrence interoperability must be validated against a deliberately selected
calendar and recipient account before relying on provider-specific behavior.
